# Current persistence audit

## Scope and method

The audit compared every migration in `supabase/migrations` with current reads/writes in CELEX, document transformation, storage download, whole-document MK1, segment workspace, approval, and report-generation code. The migrations are materially reflected in application usage; there is no generated database type layer, and `src/domain/records.ts` is incomplete relative to the evolved schema.

## Document and source path

- `projects` is the owner/language boundary. Rows are mutable (`status`, name, timestamps) and owner-scoped by RLS.
- `documents` is the logical document record. It carries CELEX/source provenance, corrigendum relationships, and PDF→DOCX derivation state. `(project_id, celex_number)` is unique when CELEX exists. A source PDF, corrigendum, and working DOCX are separate document rows.
- `document_versions` is the byte-bearing version record. `(document_id, version_number)` and `(source_storage_bucket, source_storage_path)` are unique. Source metadata is protected by an update trigger, but `raw_text`, extraction fields, counts, and diagnostics remain mutable. There is no SHA-256 column.
- CELEX import downloads and analyzes official bytes, creates/reuses document/version IDs, uploads to `source-documents`, then inserts/updates the version. Corrigenda are separate documents linked by `parent_document_id`.
- Upload paths are `<auth.uid>/<project_id>/<document_id>/<version_id>.<extension>`. The private bucket has no UPDATE policy; select/insert/delete require both owner path and owned project.
- Working DOCX transformation creates one derived document per source (`derived_from_document_id`, `derivation_type=pdf_to_docx`), then appends version numbers. Each version records `derived_from_version_id`. Generated bytes are validated, uploaded with `upsert:false`, downloaded, hash-compared in memory, and only then marked ready. The hash is not persisted.
- Deletion RPCs and application cleanup physically delete objects and dependent rows. This is appropriate for current user deletion but conflicts with future regulated retention unless artifact retention rules distinguish purge from supersession.

## Extraction and canonical data

- `document_versions.raw_text`, `extraction_status`, counts, count error, and JSON diagnostics hold mutable extraction state.
- `document_segments` is the current source segmentation table, unique by `(document_version_id, segment_index)`, with a same-version parent FK and a shallow legal path. It is lazily populated from DOCX during MK1 translation. It does not preserve OOXML nodes, inline codes, source ranges, snapshot identity, or a source artifact hash.
- There are no production `DocumentNode`, `TranslationUnit`, `InlineCode`, or immutable canonical-snapshot tables yet.

## Translation and approval

- `translations` is mutable current state, unique by source segment and target language.
- `translation_versions` is append-oriented text history. MK1 and human drafts append rows. Approval mutates the selected version's review fields and the parent translation status; it atomically creates a human-approved TM unit.
- `translation_evidence` appends generation/TM/QA/approval evidence but permits RLS-authorized updates/deletes.
- `document_translation_runs` is a mutable processing run/status record with one-active-run partial uniqueness. `document_translation_run_segments` fixes each run to exact segment and translation-version IDs.
- `approved_translation_memory_units` separates legacy trusted knowledge from project-origin human approval. AI versions are not promoted automatically.

## Existing derived artifacts

- `document_translation_artifacts` supports only `mk1_docx` and `translation_report_docx`; it stores run/version, path, filename, count, status and optional `content_hash`.
- MK1 DOCX uses `upsert:false`, one row per `(run_id, artifact_type)`, but has no byte SHA-256/size/MIME/producer lineage.
- Translation reports are mutable: when inputs change, code uploads a new object, updates the existing artifact row, then deletes the old object. This is the clearest incompatibility with immutable exports.
- The authenticated download route resolves source/MK1/report records and creates 60-second signed URLs. ZIP export downloads current source version objects directly.

## Storage and security

- `source-documents` is private, 50 MB, PDF/DOCX only. Storage RLS is path-based: owner UUID first, project UUID second. No UPDATE policy enforces object replacement resistance; delete is allowed to owners.
- Database RLS resolves ownership through project joins. Worker HTTP calls use a bearer token but the worker has no Supabase service-role persistence path.
- Phase 6B `artifacts/shadow-runs` is local diagnostic evidence only and is excluded from this production design.

## Main gaps

No durable byte hash, generalized artifact identity, processing-generation identity, multi-input lineage, canonical snapshot boundary, CAT skeleton identity, stale guards, artifact-to-translation-version mapping, or immutable export history exists. These can be added without replacing current tables or flows.
